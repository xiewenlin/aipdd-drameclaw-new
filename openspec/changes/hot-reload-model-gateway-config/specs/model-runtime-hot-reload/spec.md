## ADDED Requirements

### Requirement: Detect effective runtime configuration changes
The system SHALL compare the latest persisted runtime revision and effective Cognee configuration fingerprint at every public Cognee operation boundary, and SHALL trigger Cognee draining only when the effective connection, knowledge LLM, Embedding model, Embedding dimension, or vector-semantic parameters change.

#### Scenario: Knowledge model binding changes
- **WHEN** an administrator saves a different knowledge LLM or Embedding binding and the runtime revision increases
- **THEN** the worker marks the latest effective snapshot as desired and begins the Cognee generation transition before admitting new operations

#### Scenario: Unrelated image binding changes
- **WHEN** an administrator changes only the image-generation model binding
- **THEN** the worker advances its observed runtime revision without draining or reconfiguring Cognee

### Requirement: Preserve one runtime generation per operation
The system MUST grant each complete public Cognee operation a lease for exactly one immutable runtime generation and MUST release the lease in a finally-equivalent path.

#### Scenario: Configuration changes during ingestion
- **WHEN** the global model configuration changes while a knowledge ingestion operation holds a generation lease
- **THEN** every LLM and Embedding request in that ingestion operation continues using the leased snapshot until the operation finishes

#### Scenario: New operation arrives during draining
- **WHEN** a new Cognee operation starts while the active generation is draining
- **THEN** the operation waits and does not execute against either the draining generation or a partially applied generation

### Requirement: Apply the latest configuration without restart
The system SHALL drain the active Cognee generation and atomically apply the newest valid desired snapshot without requiring a backend process restart.

#### Scenario: Old generation drains
- **WHEN** the last active lease for the old generation is released
- **THEN** the system applies the desired environment, Cognee configuration, and client caches as one transition before granting leases for the new generation

#### Scenario: Repeated saves coalesce
- **WHEN** multiple effective Cognee configurations are saved while the active generation is draining
- **THEN** the system applies only the newest persisted desired snapshot and does not initialize superseded intermediate revisions

### Requirement: Isolate failed runtime reloads
The system MUST prevent new Cognee operations from using a partially applied configuration or silently falling back to credentials from a prior generation when runtime application fails.

#### Scenario: Client cache reset fails
- **WHEN** Cognee or LiteLLM cache reset fails during application of a desired snapshot
- **THEN** the system rolls process-global state back where possible, enters the failed state, blocks new leases, and reports a sanitized reload error

#### Scenario: API key is removed
- **WHEN** the desired Cognee snapshot has no usable API key
- **THEN** new Cognee operations fail with an explicit configuration error and never continue using the previous generation's key

### Requirement: Converge independently per worker process
Each worker process SHALL check the shared persisted runtime revision at public Cognee operation boundaries and SHALL independently converge its local runtime coordinator to the latest effective snapshot.

#### Scenario: Worker misses the save notification
- **WHEN** one worker does not receive the in-process notification generated by a settings save
- **THEN** its next Cognee operation detects the shared revision and applies or waits for the latest snapshot before executing

#### Scenario: Two workers observe a new revision
- **WHEN** two worker processes observe the same new runtime revision at different times
- **THEN** each worker safely drains and updates its own process-global Cognee runtime without relying on the other worker's memory state

### Requirement: Protect knowledge bases from incompatible embeddings
The system MUST persist a per-project Embedding signature containing the normalized model identity, effective vector dimension, and vector-semantic parameters, and MUST block incompatible reads or incremental writes until an explicit successful rebuild.

#### Scenario: Same dimension but different model
- **WHEN** an existing project's stored Embedding signature and current signature use different model identities but the same vector dimension
- **THEN** query and incremental ingestion fail with `knowledge_embedding_rebuild_required`

#### Scenario: Credential-only change
- **WHEN** only the NewAPI base URL or API key changes and the effective Embedding signature remains unchanged
- **THEN** the project remains compatible and no knowledge-base rebuild is required

#### Scenario: Explicit rebuild succeeds
- **WHEN** a user explicitly rebuilds a project knowledge base with the current Embedding configuration and the rebuild completes successfully
- **THEN** the system atomically stores the new Embedding signature and permits subsequent reads and incremental writes

#### Scenario: Legacy project has no reliable signature
- **WHEN** an existing knowledge base has no stored signature and its original Embedding configuration cannot be determined reliably
- **THEN** the system requires an explicit rebuild instead of assuming compatibility

### Requirement: Report hot-reload status safely
The model gateway status API SHALL expose the current process's desired revision, active revision, runtime state, active lease count, last applied time, and sanitized last reload error without exposing credentials.

#### Scenario: Runtime is draining
- **WHEN** a desired snapshot is waiting for active Cognee leases to finish
- **THEN** the status reports `draining`, the desired and active revisions, and the active lease count, and does not mark Cognee as restart-required

#### Scenario: Runtime is ready
- **WHEN** the latest desired snapshot has been applied successfully
- **THEN** the status reports `ready` with matching desired and active revisions and no Cognee restart requirement

#### Scenario: Runtime application fails
- **WHEN** applying the latest desired snapshot fails
- **THEN** the status reports `failed` with a non-secret actionable error and never includes the API key or raw authorization headers

### Requirement: Bound waiting without terminating active work
The system SHALL support a bounded wait for new operations during draining and MUST release all leases on normal completion, failure, or cancellation without forcibly terminating active operations solely to apply configuration.

#### Scenario: Wait timeout expires
- **WHEN** a new operation waits longer than the configured reload wait timeout while old leases remain active
- **THEN** it fails with `model_runtime_reload_wait_timeout` and the active old operations continue running

#### Scenario: Leased operation is cancelled
- **WHEN** an operation holding a generation lease is cancelled
- **THEN** its lease is released in cleanup and the pending generation transition proceeds when no other active leases remain
